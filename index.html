Event-driven ETL from AWS S3 into Snowflake

Retail CSV files dropped into S3 are picked up automatically and turned into a star schema: two dimensions and one fact table. Everything after the file lands runs inside Snowflake, using Snowpipe, streams and task chains, with no external orchestrator.

Built with AWS S3, AWS SQS, Snowflake (Snowpipe, streams, tasks, storage integration) and SQL.

What one run of a task tree does

Each entity has its own task tree. It checks every minute but only runs when its stream has new data.

  1. Pause the pipe, so no new files load mid-run.
  2. Merge the stream into the raw table.
  3. Load the dimension or fact table.
  4. Truncate the staging table.
  5. Resume the pipe.

Decisions I made

Pause the pipe for the length of each run
Staging is truncated at the end of every run. If Snowpipe kept loading, rows that arrived after the merge would be deleted by the truncate without ever being processed.
Deduplicate before merging
If an item appears more than once in a batch, row_number() partitioned by item_id keeps only the latest version, so the MERGE never sees conflicting rows.
Use streams as the trigger
Every task tree checks system$stream_has_data(), so warehouse compute is only used when new data has arrived.
Surrogate keys on the dimensions
The fact load joins raw orders to both dimensions and swaps natural IDs for surrogate keys.
Storage integration instead of access keys
Snowflake reads S3 through an IAM role, so no AWS credentials appear in the code.

Known limitations

  • The fact table is rebuilt in full on every run. Fine at this size; a larger dataset would need an incremental load.
  • The fact load uses inner joins, so an order whose customer or item hasn't loaded yet is left out until it does.
  • Both dimensions are Type 1, so item price history isn't kept.
  • There are no automated tests yet. Row-count and null checks, or moving the transformations into dbt, would be next.

Northwind data warehouse with dbt and BigQuery

A dbt project that turns the Northwind sample database (a wholesale business's orders, purchasing and inventory) into a tested, documented star schema on BigQuery, with wide "one big table" models on top for reporting.

Built while following the Analytics Engineering Bootcamp on Udemy by Rahul Prasad and David Badovinac. The fixes, tests and findings below are what I changed and added afterwards.

Built with dbt, Google BigQuery and SQL.

Decisions I made

Fixed the purchase order fact's grain
It originally joined purchase orders to sales lines on product ID alone, which duplicated each purchase line once per customer who'd bought that product. It's now one row per purchase order line, joined to a new supplier dimension.
Declared a grain for every fact
Each fact is deduplicated on its true primary key, keeping the most recent record where a date exists.
Built the one big tables from the star schema
The star schema stays the single source of truth, so the wide reporting tables can never disagree with it. A custom test checks the sales table has exactly as many rows as the fact it's built from.
Tests on every key
unique and not_null on every key, relationships tests from each fact to its dimensions, and every warehouse model documented in schema.yml.

What the tests caught

  • Every fact row failed its join to the date dimension. The calendar started in 2014, but the orders are from 2006. I extended it back to 2005, and fixed an inverted weekend flag and a wrong day-of-year column while I was there.
  • Two sales lines have a quantity of 0. They're genuine source records, so I kept them and a custom test flags them as a warning instead of silently dropping them.

Known limitations

  • Products with more than one supplier are filtered out in staging. A product–supplier bridge table would bring them back.
  • Dimensions are Type 1. dbt snapshots would add history.
  • Every model is fully rebuilt on each run. Incremental models would suit larger fact tables.

NYC taxi batch ingestion with Python, PostgreSQL and Docker

A containerised batch pipeline that downloads monthly NYC taxi trip files, loads them into PostgreSQL in chunks, and records every run. One command, docker compose up, starts the database, pgAdmin and the loader together.

Started from week 1 of the DataTalksClub Data Engineering Zoomcamp. The original script no longer ran because its data source had been taken down; the decisions below are what I rebuilt afterwards.

Built with Python, pandas, SQLAlchemy, PostgreSQL, Docker, Docker Compose and pgAdmin.

Decisions I made

Safe to re-run
Loading a month first deletes that month's existing rows inside the same transaction. Running a month twice replaces it instead of duplicating it, and a failed load rolls back completely.
Stream in chunks
A month can be 1.4 million rows, so the file is read 100,000 rows at a time with explicit column types, and never sits in memory all at once.
A run log in the database
ingestion_runs records the month, row count, status, timings and any error message. The script also exits with an error code if a month fails, so a scheduler can tell.
No credentials on the command line
Database settings come from a .env file kept out of the repo, instead of passwords typed into commands where they end up in shell history.

Known limitations

  • It runs on demand. Scheduling with cron or an orchestrator would load each new month automatically.
  • It loads raw data only. The verification queries report issues such as mis-dated trips but don't fix them.
  • Loading through pandas is slow for big months. PostgreSQL's COPY would be much faster.

Premier League standings: API to PostgreSQL to Streamlit

A Python pipeline that pulls Premier League data from API-Football, cleans it with pandas and loads it into PostgreSQL. A SQL view ranks the teams, and a Streamlit dashboard reads from that view.

Built with Python, Requests, pandas, SQLAlchemy, PostgreSQL, Streamlit and Plotly.

Decisions I made

Credentials from environment variables
The API key and database connection details are read from the environment, never written in the code.
Fail cleanly
Errors are caught and the script exits with a clear message instead of a raw stack trace.
Load in a single transaction
A failure part-way through doesn't leave a half-written table behind.
Rank in SQL, not in the dashboard
The ranking rules live in one view, so any tool that reads the database gets the same table.
Logging and a cached dashboard query
Each run logs what it did, and Streamlit caches the query so the page doesn't hit the database on every interaction.

YouTube channel analytics: API to PostgreSQL to Power BI

A Python pipeline that pulls channel and video statistics for five data-education YouTube channels from the YouTube Data API, loads them into PostgreSQL, and feeds a two-page Power BI dashboard comparing their growth and engagement: 2,274 videos in total, collected in 2022.

Built with Python, YouTube Data API v3, pandas, SQLAlchemy, PostgreSQL and Power BI.

Decisions I made

Batched API calls
The API returns at most 50 items per request, so video details are fetched 50 at a time to keep daily quota use low.
Handle hidden stats
Creators can hide like counts or turn off comments. Those values come back missing and are stored as nulls instead of crashing the run.
Atomic refresh
Both tables are replaced in one transaction, so the dashboard never reads a half-finished refresh.
Credentials outside the code
The API key and database details live in a .env file kept out of the repo.

Known limitations

  • Each run replaces the tables, so the dashboard shows a single snapshot, not growth over time. Appending a dated snapshot each run would allow trends.
  • It runs on demand, and the channel list is fixed in the script.
